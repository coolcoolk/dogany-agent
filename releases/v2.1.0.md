## Highlights

### 1. 읽는 자가 없었다

이번 릴리스에 담긴 결함은 서로 달라 보이지만 한 종류다. **이미 기록됐고, 경고됐고,
선언돼 있었다. 아무도 읽지 않았을 뿐이다.**

- 업데이트가 브릿지 파일 충돌을 보존하고 그 사실을 **두 번 출력**했다. 7개 파일이
  12일간 미착지로 앉아 있었고 그동안 브릿지 테스트는 전부 실패했다.
- 로케일 카탈로그가 드리프트 가드에 붙들린 채 그것을 읽는 코드가 착지해서,
  유저 화면에 문장 대신 **키 이름**이 떴다.
- 작업세트 게이트가 규율이 보내는 곳이 아닌 **세션 안 디스패치만** 세고 있었다.
  준수가 위반으로 집계되고, 손으로 쓴 표시가 증거로 통과했다.

그래서 이번 픽스는 전부 **새 규칙이 아니라 독자**다. 규칙은 이미 있었다.

### 2. 맡긴 일이 형님 한마디에 죽지 않는다

세션 안에서 돌던 백그라운드 작업은 형님이 아무 말이나 입력하는 순간 죽었다.
`/stop` 이 아니라 **평범한 메시지**가 방아쇠였다. 긴 작업을 자기 프로세스로
내보내는 규율이 이제 한 인스턴스의 사설 메모가 아니라 **프레임워크 정본**에 있고,
업데이트를 받는 모든 인스턴스에 닿는다.

### 3. 기억보다 기록을 먼저 본다

구조화된 원장에 이미 들어 있는 사실을 **연상 기억으로** 답하고 있었다. 답의 품질이
그때그때 기억이 얼마나 신선한지에 달려 있었다는 뜻이다. 이제 매 턴 회상보다
**원장 읽기가 먼저** 돌고, 어느 원장을 읽을지는 프레임워크에 박힌 폴더 경로가 아니라
**킷이 스스로 선언한 레지스트리**가 정한다.

목표에 매달리지 않은 안전 행(칼로리 하한, 적자 상한 등)은 **무조건** 실려 온다 --
링크만 따라가면 정확히 그런 행이 조용히 빠지기 때문이다. 모든 값은 **마지막으로
쓰인 날짜와 함께** 도착하고, 그 날짜를 대신 판정해 주지는 않는다.

### 4. 개발선과 릴리스선이 갈라졌다

캐노니컬이 상주 `dev` 브랜치와 출하 전용 `main` 을 따로 갖는다. 진행 중인 작업이
같은 자리에 앉아 있다는 이유만으로 릴리스 컷에 실려 나가는 일이 구조적으로 없다.

### 5. 산문과 복사물의 그릇이 갈라졌다

출력 계약이 코드블록 하나만 문서화하고 있어서 구조적인 것이 전부 그 한 그릇으로
갔다. 이제 **산문 / 시각적 강조(인용) / 접히는 상세(확장 인용) / 복사물(코드블록)**
이 각자 맡은 일로 갈라진다. 그릇은 길이가 아니라 **역할**로 고른다.

### 6. 답변이 검사기에 먹히지 않는다

턴 끝에 도는 검사 훅이 한 번이라도 되물으면, 그 직전에 쓴 **진짜 답변이 통째로
사라졌다.** 본문도, 첨부한 이미지도, 결정 버튼도 함께. 배달 기전이 "마지막 메시지
하나"만 최종 답변으로 보고 있었기 때문이다. 이제 **턴 전체가 한 통**으로 조립된다.
검사기가 몇 번을 되묻든 형님께 가는 것은 하나이고, 온전하다.

같은 표면에서 절 제목의 기호가 둘씩 겹쳐 나오던 것도 잡았다. 규율은 제목 기호
목록을 갖고 있었는데 **그 목록을 코드가 몰랐다** -- 1절과 같은 종류의 결함이다.
이제 목록은 코드에 있고, 표기가 흔들려도 화면은 깨지지 않는다.

### `/stop` 응답 문구 단일화 (DGN-991)

4분기 -> 2문구. `stop_interrupted` / `stop_forced` / `stop_paused` 가 동일 문장,
`stop_nothing` 만 별도. `stop_bg_note` 키 폐기 (i18n ko/en + `messages.py` +
`bot.py` 참조 제거).

폐기 근거는 실측 2건이다. "백그라운드 작업도 함께 중단" -- in-session Task
서브에이전트는 SDK interrupt 의 abort tree 로 죽지만 `dispatch-detached.sh`
산물은 자기 setsid 세션이라 생존한다. 어느 쪽으로도 단정 불가. "한 번 더 보내면
강제 종료" -- `bot.py` 의 soft-interrupt except 블록이 이미 `_hard_stop` 으로
자동 폴백한다.

`stop_paused` 통일 근거: `_hard_stop` 은 항상 3단계(턴 취소 / 스트림 종료 /
큐 비우기)를 실행하며, 분기는 사후 판정이지 별도 모드가 아니다.

### 12. 이 릴리스가 나가는 이유 -- 설치, OSS 는 다음 판 (DGN-1286 / DGN-1276)

이 판의 안정판 컷은 **새 사용자가 설치할 수 있게 한다**는 한 줄로 나갔다(형님
확정 2026-09-04). dev 컷의 결함 클래스("읽는 자가 없었다")를 정리한 뒤, 실제
설치 경험을 막던 결함들 -- 이미 설치된 Homebrew 를 매번 재설치하던 것, 로그인이
설치 화면으로 돌아오지 않던 것, 온보딩과 중복이던 owner id 질문, 킷을 안 고른
에이전트가 life-kit 습관(아침 브리핑 등)을 갖고 태어나던 것 -- 을 install
묶음(DGN-1286)으로 안정판 전용 추가 반영했다.

OSS 공개본 분리(DGN-1276, 브릿지 공개 경계를 손으로 복사하지 않고 기계로
생성)는 **v2.2 로 분리**됐다. 같은 판으로 묶지 않은 이유는 비용 비대칭이다:
install 묶음은 크기가 확정된 작업이라 끝나는 시점을 알 수 있지만, OSS 추출은
4중 게이트(생성기 자체의 테스트 스위트 포함)를 전부 통과해야 발행할 수 있고
그 완료 시점이 아직 없다. 두 작업을 하나의 컷에 묶으면 install 이 OSS 완료를
기다리며 무기한 대기하게 된다. 이번 컷에는 공개본에만 있던 수정 8건을 정본으로
되가져오는 역류 상환(DGN-1276, C1/C5/C7/C9/C10/C11/C12/C13)만 선행 착지했고,
공개본 발행 자체는 하지 않았다 -- 생성기와 4중 게이트가 착지분의 전부다.
