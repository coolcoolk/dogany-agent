## Highlights

### 1. Work you dispatched was being refused over usage

When you dispatch work to run in the background, a rule refuses it while
weekly usage is high. That rule has one exemption: work the owner ordered
directly runs anyway. The exemption existed in settings and was switched on.
But usage is checked in two places -- one honors the exemption, the other
does not know it exists -- and the one called when work actually starts was
the one that did not. So the work kept being refused even with the setting
on.

Now directly-ordered work runs even when usage is high. When a run passes on
the exemption, that fact is written to the record (stderr) -- nothing passes
silently.

How it was fixed: instead of building the same verdict a second time into
the side that did not know the exemption, that side now asks the side that
does. The two checks diverged in the first place because the same verdict
was derived independently in two places. If asking fails for any reason
(missing module / import error / unexpected output), everything falls toward
refusal -- fail-CLOSED; the stricter answer is the default. The 5-hour axis,
block-on-lookup-failure, and the sentinel semantics did not change by a
single character.

**Unresolved (same axis, separate matter)**: the rule that relaxes the block
when the usage reset is close (reset-proximity relief) still exists in only
one of the two places. Measurement at the time of the work read 7-day usage
at 95% with 5.4 hours to reset -- inside the relief window, and the other
side does not know it. The root fix is to unify the verdict itself into one
place; that is tracked separately.

### 2. Service names no longer differ by install type

It is the same program, but the background service name differed by install
type (public build vs. canonical), and the code picked the name by branching
on which install it was running in. So if an update ran under a different
name than the one used at install time, the timer registered under the old
name could be left behind undeleted.

Now the name is a setting, not a branch. The resolution order is **explicit
setting > name already registered on this host > public default**. The
middle step -- adopt the name already registered -- works in both
directions, so a host installed under either name updates without leaving an
orphaned timer.

    BRIDGE_UNIT     default claude-code-telegram.service
    WATCHDOG_UNIT   default claude-code-telegram-watchdog

**Existing installs need to do nothing.** The values confirmed by measuring
the artifacts are exactly the defaults above.

### 3. Generating the public build automatically is ready (not shipped yet)

There is machinery that generates the public build from the canonical
automatically. Its 7 checks that make sure nothing ships that should not
(estate prose / ticket IDs / reference audit / consumer suite / landing
delta / version consistency / secret-sweep) all pass now. The 3
reference-audit findings that used to fail predate this work; they were paid
down along the way. The public repo's top 3 files (README / CHANGELOG /
VERSION) are files this machinery by design does not touch, so drafts were
placed as staging copies.

This release does **not** execute that publication. What remains is one
command line (`--execute`), and that is an act that needs separate owner
approval.

### 4. Korean and English mixed inside one work-board line

On the work-board screen pinned in Telegram, the prefix attached to each
in-progress item was hardcoded as an English internal term. The section
label right next to it is Korean, so two languages appeared mixed inside one
line. This is the first screen an external user meets.

Now the prefix comes out as a neutral Korean default, and each instance can
swap it. The way to swap it is the same one the surrounding 3 labels already
used (environment variable → config file → default). No new rule was
invented; one more rider was put on a rule that already existed.

**Left as separate items**: task names still appear as English slugs, and
the model name is not shown. The former is a change to the interface that
dispatches work itself, and pulling it into this release would delay it.

### 5. Exemptions were ignored when sweeping a different folder

The gate that stops files from going out has two legitimate exemption
paths -- attach a review ticket, or put the file on an allowlist. But those
paths only recognized files **inside the folder being scanned.** Point the
sweep at a different folder (a different checkout), and the exemption paths
might as well not have existed.

Now both work from outside:

- A review ticket given as an absolute path is accepted as-is (`.md`
  extension required). Relative-path behavior did not change by a single
  character -- every existing caller is unaffected.
- One new environment variable supplies an extra allowlist. It does not
  replace the scanned folder's own allowlist -- the two are **merged.**

5 regression tests pin both paths.

### 6. Install step numbers were displayed wrong

The install screen's `[N/M]` step display disagreed with itself about the
total number of steps.

Investigation showed the reported `[1/2]` was **not** a step number but a
separate two-choice question (that string is pinned by a regression test and
must not change) -- and instead there was a third notation nobody had
reported: a step inserted later had been missed when the numbers were
redone. **The install actually has 10 steps, not 9.** Everything now shows
`[N/10]`, and why `[1/2]` alone is the exception is written down in both the
code and the tests.

As a side repayment, a test nondeterminism is gone too: when the
step-display check failed, the following continuity check would pick up the
leftover values in arbitrary order. That path is cut off.
